## 简介

SilverMoon Terminal（银月终端）是一款基于 Electron 的桌面端定制数据库应用，提供本地化的数据查询、编辑与管理功能。数据存储于本地 SQLite 数据库，无需网络即可离线使用。

除常规的数据库管理功能外，应用还内置了仿桌面系统的**终端板块**，提供养成计算、抽卡记录拉取、账号数据看板、大地图标注、祈愿概率模拟等一系列小工具。

开发目的为个人使用，感兴趣的话欢迎体验，请勿传播。

## 主要功能

- 📊 **数据浏览与编辑** — 角色、武器、圣遗物、材料、食物、书籍、祈愿、挑战、游戏数据等板块的表格/画廊双视图，支持增删改查、批量操作、多列排序与筛选
- 📖 **书籍板块与阅读器** — 107 部书籍（含 310 卷正文），元数据取自 bilibili wiki、正文取自米游社观测枢；全屏阅读器支持滚动/章节双模式、三主题、四档字号，并与角色故事共用
- 🖥️ **终端板块** — 仿桌面系统：桌面图标网格（自由拖拽、框选、群组移动、右键收起）、Dock 菜单栏、可拖拽/缩放/全屏的独立应用窗口（macOS 风格吸入/展开动画），内置 12 个应用 + 3 个系统工具
- 📦 **资源库** — 参考 iOS App 资源库：全局快捷键（Ctrl+Tab / control+Tab）呼出小窗，按拼音排序浏览全部小程序，可拖拽图标到桌面重新添加，快捷键可自定义
- 🧮 **养成计算器** — 角色升级/天赋培养材料需求计算，双端范围滑块设定区间，旅行者元素切换，支持从世界树账号一键填入当前练度
- 📈 **祈愿分析** — 基于数据库词条建模的精确概率引擎（列式马尔可夫 DP），多卡池抽取顺序规划、蒙特卡洛模拟验证
- 🎰 **祈愿捕捉站** — 米哈游官方登录（扫码）拉取抽卡记录，五星时间线可视化，按 UID 多档案管理
- 🌍 **摹忆中枢** — 交互式原神大地图：分层切片渲染、标点/文本框标注、分层地图（地面/地下/地上层）、地图标定与开发者工具
- 🎴 **希穆兰卡 · 祈愿模拟器** — 五池（角色/角色池-2/武器/集录/常驻）逐抽模拟：自定义卡池安排与初始资源（支持从北国银行导入明细）、从祈愿板块导入历史卡池、从祈愿捕捉站导入垫池与历史记录；卡池背景由「数据库图片 + 代码 + 字体」合成（非官方卡池图），抽卡动画为「星轨 → 爆发 → 逐件展示 → 罗列」并带星级专属特效与捕获明光五彩流星，可一键关闭动画、可关闭祈愿确认弹窗；实时抽卡记录（区分模拟前/模拟中）与统计，多存档「继续进度=另存为」
- 🏦 **北国银行** — 按日期的原石/纠缠之缘/创世结晶/星辉收支记账，差额自动换算，联动祈愿分析
- 🌳 **世界树** — 米游社账号数据看板：探索度、角色面板、深境螺旋/剧诗/危战挑战、实时便笺、圣遗物练度分析（有效副词条/权重/评级）

- 🎨 **主题定制** — 9 套内置主题 + 自定义配色方案，元素颜色可独立配置
- 🔍 **全局搜索** — 各板块内快速检索所有数据
- 💾 **备份与恢复** — 数据库自动/手动备份，支持导入导出、多基准库切换
- 🔄 **软件更新检查** — GitHub Release 发布
- 🌐 **网站收藏** — 内置常用网站快捷访问

## 开发提示：测试脚本与磁盘

`scripts/*.cjs` 会用 Electron 起真实主进程，需要一份可写的数据库 + 图包。图包（`images-*`）有 1.7 GB，
**禁止**用 `fs.linkSync` / `fs.copyFileSync` 直接搬进临时目录 —— 硬链接跨 APFS 卷必然失败，
会退化成每次运行真复制 1.7 GB，历史上曾因此堆积掉 12 GB 磁盘。

统一改用 [`scripts/lib/sandbox.cjs`](scripts/lib/sandbox.cjs)：`cloneTree()` 走 APFS 写时复制克隆
（1.7 GB 实测只占 9 MB）、`sweepLeftovers()` 启动自愈、`installCleanupHook()` 保证退出必清、
`guardSandboxSize()` 在克隆退化时立刻告警。

**磁盘莫名变少时先跑 `npm run clean:temp`** —— 它会汇总并清理 TMPDIR 下所有 `silvermoon-*` 测试残留
（异常终止如 SIGTRAP/SIGKILL 会绕过一切退出钩子，只能靠这个和启动自愈兜底）。
详见 [开发约定](doc/开发约定.md) 铁律 E。

## 板块功能详解



### 1. 数据管理板块（角色 / 武器 / 圣遗物 / 材料）

四类实体均采用「列表页 + 详情页」结构，共享同一套架构：

- **列表页**：表格/画廊双视图（武器额外有"装备"密集小图标视图）；支持搜索、多列排序、筛选（角色支持 7 元素图标多选筛选条）、多选批量删除、右键菜单；行右键可直接唤起养成计算器；所有状态（视图模式/搜索/排序/滚动位置）自动持久化，返回列表时精确恢复滚动位置
- **详情页**：横幅 Banner + 可折叠模块卡片 + 图片灯箱；编辑弹窗支持图片导入（拖拽/文件选择器）与改 ID 时级联更新关联表

| 板块 | 特色 |
|------|------|
| **角色** | 9 个可开关模块：基本信息（等级/元素滑块切换面板属性）、天赋技能（Excel 风格倍率表，支持直接粘贴 Excel/TSV）、命之座、培养素材、角色故事（全屏阅读器，三主题 + 章节/滚动双模式）、衣装（点击切换激活衣装并联动列表头像）、特殊料理（同时给出**食物板块条目**与**料理原型**两个跳转入口）、名片、图库（多图拖放导入）；相关效果引用库（`[effect:名称]` 标记自动展开） |
| **武器** | 三视图列表；详情页精炼滑块 1~5 实时替换被动描述各精炼等级下的倍率；武器分类（武器/武器装扮/TPS） |
| **圣遗物** | 编辑表单覆盖五件套完整文案与图片；详情页五部件 Tab 联动查看（名称/图片/介绍/故事四维切换） |
| **材料** | 9 类材料类型（角色突破/武器突破/天赋书/料理/特产/通用/掉落/周本/活动）彩色胶囊徽章；类型中英文自动归一化；详情页底部「用于烹饪」反查全部料理，并支持人工增/删/改关联与用量 |

### 2. 食物板块

食物的数据模型与其它板块不同：**同一道菜在游戏里有「奇怪的 X / X / 美味的 X」三种形态**，本站把它们合并成一个条目（`foods` 主表 + `food_variants` 形态表），列表默认只显示普通版本，详情页可切换对比——三种形态共用同一张游戏图标，因此用配色、边框与图片滤镜（奇怪=压饱和压暗 / 普通=原色 / 美味=提亮增艳）做视觉区分，简介与效果各自独立。

- **列表页**：画廊视图为默认（表格视图可切换）；搜索、多列排序、筛选（ID / 稀有度 / 名称 / 类型 / 功效 / 地区 / 效果）。**搜索栏可以直接搜角色名**——搜「琴」会同时给出她的特殊料理「提神醒脑披萨」与它的原型「烤蘑菇披萨」，结果卡片/名称列上用 `琴·特殊料理` / `琴·原型` 角标说明这条为什么被搜出来（角标只在搜索时出现，平时浏览不加）。**功效与地区是从数据里汇总的预选项下拉**——功效按「、」拆成单项（如「提升防御」「提升治疗效果」）做包含匹配，选项后标注条目数并按出现频次排序；卡片右上角三点标记表示该条目含三形态，卡片角标提示暂无烹饪材料；「多选模式」开启后浮动操作条可全选/批量删除，选中项实时同步给开发者工具栏
- **返回保留**：视图模式、搜索词、多列排序、筛选条件与筛选栏展开状态都会随滚动位置一起落盘，从详情页返回后原样恢复
- **详情页**：三形态横向对比条（点击切换）+ 选中形态的完整简介与效果；「烹饪材料」区块列出配方与数量，点击材料卡片直达材料板块；材料详情页反向提供「用于烹饪」区块列出全部料理，两侧都支持人工增/删/改
- **特殊料理 ↔ 料理原型**：每道特殊料理都是某道基础菜的衍生版本，两侧互相给出入口——特殊料理页的「料理关系」列出**料理原型**（头部还挂一枚可点的「原型 X」胶囊），基础菜页反向列出**衍生特殊料理**，角色页的特殊料理模块也直接给出原型入口，列表页搜索角色名也会把两道菜一起带出来。关联没有外键，锚点是**基础菜身上的 `special_char`**（含义是「这道菜能变成谁的特殊料理」），规则集中在 `src/utils/dishLinks.js`（详情页走 SQL 版、列表搜索走同口径的纯函数版）；`special_char` 缺失的条目（早柚「头晕回避术・改」、薇斯纳「霜冻冰花汤」）按 `characters.dish_name` 兜底，实在查不到就不显示入口（不会假跳转/假搜索）
- **爬虫**（位于开发者工具栏，需开发者模式）：列表页勾选条目、或停在某个食物详情页时点「食物爬虫」批量覆盖；「查漏补缺」比对线上目录后按五类缺口分组（未收录 / 缺烹饪材料 / 形态不全 / **缺料理原型** / 缺图片或简介）勾选补爬——最后一类列的是"特殊料理找不到原型"的**候选基础菜**（同一份食谱的所需食材完全一致，故可能有多个候选），补爬它们即可让 wiki 的「特殊料理角色」字段回填进库

| 数据项 | 来源 |
|--------|------|
| 名称 / 图片 / 稀有度 / 简介 / 效果 / 获取方式 / 三形态归属 | [nanoka](https://gi.nanoka.cc/item) `zh/item_all.json`（筛选 `type === '食物'`，按名称前缀与 `food_quality` 归并三形态） |
| 烹饪材料与数量、功效类别、地区、食谱获取 | [biligame wiki](https://wiki.biligame.com/ys/食物一览) 的 `{{食物图鉴新}}` 模板「所需食材」字段（MediaWiki API 批量取 wikitext，40 条/请求） |
| 特殊料理角色 / 特殊料理（**料理原型关联的锚点**，填在基础菜上） | 同一模板的「特殊料理角色」「特殊料理」字段（补爬基础菜即可回填） |
| 上述缺失时的兜底 | [米游社观测枢](https://baike.mihoyo.com/ys/obc/channel/map/189/21) `entry_page` 接口的 `material_base_info` 组件 |

> 配方里的材料名会映射到 nanoka 物品 ID 写入 `materials` 表（类型为「食材」/「地区特产」/「通用掉落」），因此食物与材料板块共用同一份材料实体；材料改 ID 时 `food_materials` 会随之级联更新。

> 图片按**内容魔数**判定真实格式后落盘（nanoka 的素材实际是 webp）：下载器读到历史遗留的「.png 结尾的 webp」会就地改正扩展名，并把纠正后的文件名回传给写库逻辑，库里存的始终是真实文件名。

### 3. 书籍板块

书籍同样是一对多的数据模型：**一部书由若干卷（章）组成，正文按卷独立**，因此用 `books` 主表 + `book_volumes` 卷表（卷序 `volume_no` 是排版与阅读顺序的唯一依据）。两个来源各负责一半：

| 数据项 | 来源 |
|--------|------|
| 名称 / 稀有度 / **体裁** / **国家** / **实装版本** / 是否收录图鉴 / 卷名 / 每卷描述 | [biligame wiki](https://wiki.biligame.com/ys/书籍一览) 的语义化查询 `action=ask&query=[[分类:书籍]]`——**一次请求返回全部 105 本**（含 308 卷的卷名/获取地点/描述/正文 wikitext） |
| 卷正文 / 作者 / 获取方式分类 | [米游社观测枢](https://baike.mihoyo.com/ys/obc/channel/map/189/68) `channel_id=68`（93 本）+ 逐条 `entry_page` 的 `modules[]` |
| 封面 | wiki 的 `File:<书名>.png`（195~220px，尺寸稳定）优先，观测枢 `icon` 兜底 |

- **列表页**：画廊视图为默认（表格视图可切换）；搜索、多列排序、筛选（ID / 稀有度 / 书名 / 体裁 / 国家 / 实装版本 / 卷 / 正文 / 作者 / 获取方式）。**体裁、国家、实装版本都是从数据里汇总的预选项下拉**（多值字段按「、」拆成单项），选项后标注条目数；卡片右上角标卷数、左上角圆点表示收录图鉴、左下角圆点提示尚无正文；多选模式下可批量删除，选中项实时同步给开发者工具栏
- **快捷阅读**：右键「开始阅读」或 `Alt+点击`卡片，**就地**弹出阅读器（不跳详情页，避免先渲染一遍详情再盖遮罩的闪烁）
- **主键规则**：`books.id` **直接用米游社观测枢的 content_id**——就是观测枢网址 `baike.mihoyo.com/ys/obc/content/<id>/detail` 里的那个数字（《至冬国通史》= 509470），所以详情页路由、列表里的 ID 与线上完全对得上。观测枢只收录了 93 本，**wiki 独有的 15 本**（都是图鉴=否 的任务/隐藏书籍）没有观测枢页面，落到 `900001` 起的本地段位——一眼能看出「这本线上没有页面」，也不会与任何真实 content_id 撞号；号段取「最小空闲号」，已存在的条目永远不会被重新编号
- **详情页**：封面 + 书名 + 稀有度 + 体裁/图鉴徽章 + 国家/版本/作者/卷数概览；「卷」区块逐卷列出卷名、描述、获取地点，点击任意卷直接进入阅读器；每卷可单独增/删/改（正文走彩色标记编辑器）
- **阅读器**：与角色故事共用同一个组件（见下），目录即卷列表，支持滚动/章节双模式、暗色/仿古/亮色三主题、四档字号、`F` 切换模式、`A/D` 翻卷、`Esc` 关闭；**按书记忆上次读到第几卷**
- **插图**：正文里的 `[[file:插图.png]]` 会被转成 `[img:文件名]` 占位标记，图片按内容魔数落盘后把真实文件名回填进标记；阅读器把标记渲染成块级插图，**点击后交给通用图片观看器**（Lightbox：滚轮缩放 0.5x~8x、拖拽平移、长按 ±／一键回正），顶栏还会显示「N 张插图」。观看器挂在阅读器顶层并把层级抬到 300——正文外面套着章节切换动画的 `translate-x-0`，在里面渲染会让 `fixed inset-0` 变成相对正文一栏定位；同时阅读器在观看器打开时让出 `Esc`/`F`/`A`/`D`，一次 `Esc` 只关观看器
- **爬虫**（位于开发者工具栏，需开发者模式）：列表页勾选条目、或停在某本书详情页时点「书籍爬虫」批量覆盖；「查漏补缺」比对两站目录后按五类缺口分组（未收录 / 缺筛选元数据 / **正文需修复** / 缺正文 / 缺封面或描述）勾选补爬；「正文需修复」专门捞旧版爬虫写坏的数据——线上有插图而库里一张都没有，或正文里还留着 UNIQ 占位符

> **跨源配对的三个坑**（规则集中在 `electron/book-crawl.cjs`，可用 `npm run test:book` 单独校对）：
> 1. 观测枢 `modules[]` 的**顺序不等于卷序**（《清泉之心》是 一/四/二/三），按位置配对必错——只能按卷名/卷序号/末段名依次尝试配对。
> 2. 观测枢对**没有正文的卷会拿「描述」冒充正文**（《白之公主与六侏儒》卷二~卷七、《丘丘语诗歌试作》卷二~卷三），直接落库会得到「正文就是简介」的假书。判据是正文与描述归一化后相同（wiki 侧的描述是最可靠的对照），识别出来后回退 wiki 正文；两边都没有就如实留空。
> 3. 两站卷名写法不同：`·卷一` ↔ `第一卷`、`提瓦特游览指南·蒙德篇` ↔ `——蒙德篇——`、`谁人的日志·第二卷·瑶光滩` ↔ `谁人的日志·瑶光滩`，需要「全名 → 卷序号 → 末段名 → 顺序」四级回退。
>
> 书名层面则靠归一化（去空白、统一 `·`/`•`/`・`、去末尾括号注释）匹配，实测 wiki 的 89/105 本能命中观测枢；`与神性同行` ↔ `与神性同行·序言` 这类前缀关系再补一次前缀匹配，而观测枢对同一作品的重复建页（《林间风·故事拔萃节选》另有独立条目）会被跳过。wiki 未收录、只有观测枢有的条目（任务书籍《残破的笔记》《风、勇气和翅膀》）也会收进来，共 107 条。

> **正文插图与 SMW 占位符**：`action=ask` 返回的 `卷N内容` 是 **SMW 存储值**，其中的 `<tabber>` / `<nowiki>` / `<ref>` 已被 MediaWiki 换成 `` "`UNIQ--tabber-00000000-QINU`" `` 这样的占位符——《出发吧！嘟嘟可》的两张插画就藏在被换掉的 `<tabber>` 里。爬虫对**含占位符的书**（实测 4 本）额外取一次页面原文（照样是批量请求），用 `{{书籍}}` 模板的原始值重解析；`<tabber>` 取第一支（空/荧的性别分支取「空」），`<nowiki>` 原样保留，`<ref>` 就地展开成括号注。占位符另有兜底清理，绝不入库。

> 版本字段取自 wiki 的语义化属性（模板已把「月之一」这类月相别名映射成 6.0，爬虫再兜一层），多值用「、」合并后按版本号排序。

> **bilibili wiki 的反爬**：不带 `Referer` 的 API 请求会被 WAF 拦下并返回 `HTTP 567`（一个 JS 挑战页而不是 JSON）——浏览器里因为同源导航天然带 Referer 所以碰不到，主进程直连必须自己补。`fetchJson` / `fetchText` 里按域名统一补 `Referer: https://wiki.biligame.com/ys/`（食物配方、往期祈愿、书籍目录三条链路一起受益），并把 567 翻译成可读错误。
> 书籍目录（`action=ask`，约 2MB）成功一次就落盘到 `<数据库目录>/cache/book-catalog.json`；**只在实时请求失败时**回退这份缓存（不做"多久之内直接用缓存"的新鲜度窗口，查漏补缺要的始终是最新目录），回退时接口返回 `stale/cachedAt`，查漏弹窗会显示黄色提示；连缓存都没有时如实报错，不会假装"数据已齐全"。

### 4. 通用阅读器

## 快速开始

### 环境要求
- **Node.js** >= 18
- **npm** >= 9
- macOS (arm64) 或 Windows (x64)

### 安装与运行

```bash
# 1. 克隆仓库
git clone https://github.com/ParteaDream/SilverMoon-Terminal.git
cd silvermoon-terminal

# 2. 安装依赖
npm install

# 3. 开发模式（Vite + Electron 热重载）
npm run electron:dev

# 4. 仅启动前端（浏览器预览，部分功能受限）
npm run dev
```

### 构建

```bash
# macOS (ARM64)
npm run electron:build

# Windows (x64)
npm run electron:build:win

# 构建产物在 release/ 目录下
```

### 发布（GitHub Release）

```bash
# 构建 + 发布 macOS 与 Windows（先 macOS 再 Windows，两次独立运行）
npm run electron:publish

# 只发某一个平台
npm run electron:publish:mac
npm run electron:publish:win
```

发布内容只包含**必要的安装文件**与**更新检测元数据**：

| 平台 | 上传文件 |
| --- | --- |
| macOS | `SilverMoon-Terminal-<版本>-arm64.dmg`（安装包） |
| Windows | `SilverMoon-Terminal-Setup-<版本>.exe`（NSIS 安装包）、`SilverMoon-Terminal-<版本>.exe`（免安装版） |
| 更新检测 | `latest-mac.yml` / `latest.yml`（客户端「检查更新」只读这两个文件） |

> 本地 `release/` 里的 Windows 文件名带空格（`SilverMoon-Terminal Setup 2.1.1.exe`），上传到 GitHub 时空格会被替换成 `-`，`latest.yml` 里引用的也是替换后的名字。

mac 的 zip 包是自动更新专用的冗余产物（约 106MB），已不再构建与上传。

> **Windows 打包依赖 electron-builder 的 nsis / winCodeSign / wine 工具链**，它们默认从 GitHub Releases 下载，国内直连会失败。
> 仓库已在 `package.json` 的 `config.electron_builder_binaries_mirror` 里配置 npmmirror 镜像，走 `npm run` 时自动生效；
> 手动执行 `npx electron-builder --win` 时需要自行 `export ELECTRON_BUILDER_BINARIES_MIRROR=https://registry.npmmirror.com/-/binary/electron-builder-binaries/`。

发布后自检（确认 yaml 齐全、安装包没有停在上传中途的半截状态）：

```bash
node scripts/release-check.mjs            # 只读检查，有问题时退出码为 1
node scripts/release-check.mjs --repair   # 补传缺失/半截/与 yaml 大小不符的文件（含配套 .blockmap）
node scripts/release-check.mjs --prune    # 清理不被任何 yaml 引用的多余资产
```

> ### 首次启动步骤
>
> 1. **将 .app 移到「应用程序」文件夹**（不要放在「下载」中，macOS 对其限制更严）
> 2. **运行解隔离脚本（推荐）**
>    ```bash
>    bash scripts/fix-mac-quarantine.sh
>    ```
>    脚本会自动查找 .app，移除隔离属性并执行 ad-hoc 签名。
>
> 3. **右键 → 打开（首次必须！）**
>    在 Finder 中**右键**点击 `SilverMoon-Terminal.app` → 选择「打开」，在弹出的对话框中点击「打开」。之后就可以正常双击启动了。
>
> ### 备选方案
>
> - **手动清除隔离**：在终端执行 `xattr -cr /Applications/SilverMoon-Terminal.app`
> - **系统设置允许**：打开 **系统设置 → 隐私与安全性 → 安全性**，在页面底部点击「仍然允许」
>
> > 💡 若以上方法均无效，请确认已将 .app 移出**下载**文件夹，并确保运行了 ad-hoc 签名（`codesign --force --deep --sign -`）。<br>
> > 每次从新版本替换 .app 后，都需要重新执行上述步骤。

## 图包管理

SilverMoon Terminal 支持从数据库文件夹自动识别图包。任何名称包含 `images` 的文件夹都会被识别为图包。

### 自动选择优先级
1. **`images-版本号-类型`** 格式的文件夹优先（版本越新越优先，同版本 `Extreme` > `Medium` > `Lite`）
   - 示例：`images-1.2.0-Extreme` > `images-1.1.0-Medium`
2. 名称为 **`images`** 的文件夹（精确匹配）
3. 剩余文件夹中**大小最大**的

### 手动选择
进入 **设置 → 通用 → 图包管理**，可手动选择使用的图包，或点击"恢复自动"回到系统默认优先级。图包下载支持 CDN 增量更新（对比远程 manifest）、断点续传与多余文件清理。

## 数据架构

- **双库模式**：基准库（`silvermoon_terminal-v{version}.db`，种子数据）+ 用户库（`user.db`）。非开发者模式下，用户的增删改通过 `_user_delta` 增量表记录并合并读取，数据库更新时用户修改不丢失；开发者模式可直接写基准库
- **用户库附加表**：`worldtree_build_configs`（圣遗物练度分析有效副词条/权重配置，按角色存）、`betamemo_tasks`、`northlandbank_records`、`wish_analysis_plans`、`wish_sim_archives`（希穆兰卡模拟存档，含方案/资源/历史/保底）、`genshin_accounts`（世界树）、`gacha_archives/gacha_items`（祈愿捕捉站）、`map_marker_placements` 等
- **用户配置（user.json）**：开发者模式开关、默认启动页、默认视图模式、衣装选择、终端桌面图标（`terminalDesktopIcons`，小程序默认不自动上桌面）、终端壁纸、资源库快捷键（`libraryShortcut`）等
- **图片体系**：图片按文件名存储于图包目录，渲染层经 IPC 读取 base64，带 LRU 缓存与并发队列；支持懒加载与拖放导入
- **彩色标记文本**：`[color=#xxxxxx]` / `[b]` / `[i]` / `[note="附注"]` BBCode 风格标记，全应用统一解析渲染，编辑器支持所见即所得编辑
